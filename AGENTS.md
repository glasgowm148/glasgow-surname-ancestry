- Complete authorized work end to end. Infer routine details from context and ask only when missing information would materially change the result or required authorization for an irreversible or out-of-scope action is absent.
- Read only the files and documentation the task needs. Use referenced project docs when their subject applies instead of loading them before every change.

Commit completed coherent batches separately when helpful. Do not push; the owner handles pushes. Do not create empty commits or include unrelated pre-existing changes. The orchestrator owns staging and commits for delegated work; report any failed check or commit blocker explicitly.

- When the user explicitly corrects a repeatable workflow or quality rule governed by a project-owned skill, update the applicable `SKILL.md` during the same task so the correction persists.
- Keep durable corrections narrowly scoped. Do not automatically modify system, third-party, unrelated, or non-writable skills, and do not encode one-off preferences as universal rules.

## Research database (authority)

- `data/private/workbench/glasgow.sqlite` (genealogy-research-workbench, `genealogy.toml` `[storage]`) is the only authority for relationship claims and their assessments, and holds the migrated people, records, mentions, identity attributions, vital assessments, findings, questions, searches, parent hypotheses, studies, WikiTree observations and redirects, the update queue and the exact-file publication approvals, with every research file referenced by hash. See `docs/workbench-migration/README.md`.
- Record relationship assessments only through the workbench (`.venv/bin/genealogy --project . assess glasgow-assertion:<id> --expected-revision N …`, `relationship add`, or `genealogy proposal check|diff|apply` for batches), then run `make research-views`. Never hand-edit `research/relationship_assessments.json` or `research/relationship_probability_estimates.json`; they are generated, and `make check-workbench` fails if they differ from the database. A stale-revision error means someone else changed the assessment: re-read it and regenerate the change, never force it.
- Findings (`research/latest-findings.json`), canonical records (`research/canonical_records.json`) and vital assessments (`research/vital_assessments.json`) are also generated from the database. Write the row in the file's own format to a scratch JSON file and record it with `.venv/bin/python tools/research_entry.py upsert finding|record|vital ROW.json` (`show KIND ID` prints the current row and its revision; changing an existing row needs `--expected-revision N`). The tool regenerates the file. Never edit these files by hand: `make migrate-workbench` keeps a hand edit as a conflict without applying it, and `make check-workbench-views` fails.
- Research plans (`research/<ID>/research_plan.json`), parent-candidate lists (`parent_candidates.json`), the WikiTree update queue (`data/wikitree/profile-update-queue.json`) and its review files (`research/research-queue-matches.json`, `research/research-queue-overrides.json`) are held in the database row by row and regenerated: edit the file, then record it with `.venv/bin/python tools/research_entry.py document PATH --expected-revision N` (`document PATH --show` prints N before you edit). A new case's first plan (written by `src/wikitree_family_export.py`) is picked up by `make migrate-workbench`.
- Editorial presentation (`research/<ID>/presentation.json`, findings logs, briefs and drafts) stays in files; the database references them by hash and `make migrate-workbench` keeps the questions extracted from presentation files current. Do not create new parallel JSON registries.
- Never edit the SQLite file directly, commit it, or copy it into `www/`; backups use `.venv/bin/genealogy --project . backup create --exclude-root repository`.

## Live WikiTree editing via the local CDP browser

When asked to edit WikiTree profiles directly, drive the logged-in local Chrome over
CDP (port 9333). Use the helpers in `tools/wikitree/`: `wt.mjs` (navigate + read state),
`wt_edit.mjs` (apply an edit), `wtmgr.mjs` (check manager status). Env `TAB=wikitree`
targets the WikiTree tab.

Workflow and gotchas (all discovered 17 Sep 2026, do not re-derive):

- **Scope first**: `node wtmgr.mjs <ID>` reads each profile page and reports "Profile manager: <name>" and whether an Edit link is present. On profiles the signed-in account manages, apply the full evidence-led workflow. On profiles managed by others, add only facts taken directly from a concrete, cited record (e.g. an inspected civil register entry): additive text, citations, and more specific or corrected dates and places. Do not add speculative relationships, reattach or detach parents, merge, or restructure their biographies. Never message anyone or propose merges with non-managed profiles.
- **Text edits need the enhanced editor OFF**: otherwise `wpTextbox1` changes are silently dropped (only the structured date/place fields persist). Click `#toggleMarkupColor` ("Turn Off Enhanced Editor") before setting the textarea value.
- **Family (re-parenting)**: `Special:EditFamily&u=<uid>&who=father|mother`. To replace a father: pick `editAction_connectExisting`, enter the target WikiTree ID in `#mName`, Continue, then `#addNewPersonButton` ("Proceed to connect father") — optionally fill the explanation first. To remove a parent, pick `editAction_remove` then Continue (no confirm). Always verify the resulting profile's Family section.
- **Edit form**: the "edit" link on a profile points to `https://www.wikitree.com/index.php?title=Special:EditPerson&u=<numeric uid>` (extract `u=` from the href). The form is a MediaWiki-style POST: `#editform` with `wpTextbox1` (full wikitext), date/location fields `mBirthDate`/`mBirthLocation`/`mDeathDate`/`mDeathLocation`, and `mStatus_*` certainty radios (`guess`/`certain`/`before`/`after`/`blank`). Read `wpTextbox1` first and preserve all existing text/refs; only append/adjust what the evidence changes.
- **Summary unlock**: fill the change explanation by first clicking a summary-suggestion radio (ids `summarySuggestion-bio`, `summarySuggestion-sources`, etc.) with a trusted click, then optionally set `wpSummary` ("Summarize your changes here (REQUIRED for Full Save)") and dispatch `input`+`change` events. Full Save only commits once this is satisfied.
- **Save requires a TRUSTED click**: `el.click()` (untrusted) and `form.submit()`/`requestSubmit()` only trigger an autosave draft. Click `#wpSave` ("Full Save: Commit Changes") with CDP `Input.dispatchMouseEvent` (mousePressed + mouseReleased) at its `getBoundingClientRect()` centre. Success lands on `…/<ID>&errcode=saved`; then verify the profile `/wiki/<ID>` shows the new values.
- **Pending drafts block the form**: a failed attempt leaves an "uncommitted draft"; revisit `Special:EditPerson` and if `#wpSave` is absent, follow the "Discard the Draft" link (`…&dd=<id>`) first. A `?displayDraft=1` profile view can hang the tab — avoid it; discard via the EditPerson interstitial instead. Do one edit per call, verifying the profile each time.
- The mac-mcp browser tools work (verified 23 Sep 2026 against the research Chrome, where "Allow JavaScript from Apple Events" is enabled): `browser_list_tabs`, `browser_do` navigation and DOM `browser_observe`. Visual capture (`visual='full_page'`) can fail on sites that block injected scripts (e.g. GRONI); use CDP there. If two Chrome instances are running, check which one mac-mcp is addressing.
